Why? Technology choices and trade-offs
Backend
Django + DRF
Batteries-included: ORM, migrations, auth, admin · all built in. Python is natural for financial math (inflation adjustment, CAGR, weighted averages, FX translation). DRF gives serialization and viewsets with minimal boilerplate.
Trade-off: Synchronous views. Acceptable because slow provider work moved off the request path · stale data is served immediately and refreshed by a Celery worker; only outright cold tickers pay the synchronous fetch.
DRF (Django REST Framework) · the standard library for building REST APIs in Django. Provides serializers, viewsets, authentication, and content negotiation.
PostgreSQL
Financial data is inherently relational · earnings belong to tickers, tickers have balance sheets, users own favorites. ACID guarantees matter when writing quarterly financials. Trigram indexes (pg_trgm) give sub-millisecond fuzzy search over 23K+ tickers; unique constraints prevent duplicate data on re-sync.
Trade-off: Heavier than SQLite for a single-server app. Worth it for concurrent writes, proper indexing on LookupLog for quota queries, and production reliability. SQLite used in dev for zero-config convenience.
Redis
One process, three jobs: three-layer response cache (raw provider payloads → computed view payloads → pre-warmed popular tickers), Celery broker, and date-keyed rate-limit counters for the MCP endpoint. Eliminates most external API calls entirely.
Trade-off: One more service to run. Cheap · a single instance with a 50-connection pool covers the peak home-page fanout.
Gunicorn
Standard WSGI server. Simple. Battle-tested. Five workers behind nginx · no configuration complexity.
Trade-off: No WebSocket support. Not needed · all data flows are request/response.
WSGI (Web Server Gateway Interface) · the standard protocol between Python web apps and web servers. Gunicorn spawns worker processes that each run a copy of the Django app, handling concurrent requests.
Session auth (not JWT)
Next.js proxies API calls to Django · sessions just work. No token refresh logic, no client-side token storage, no JWT library. CSRF exempted for same-origin API calls; CORS handles cross-origin.
Trade-off: Sessions are server-side state. Fine for a single-server deployment. Redis is already in place as a session store if horizontal scaling ever becomes necessary.
Frontend
Next.js 16 + React 19 + TypeScript
Full-stack React framework with file-based routing, server-side rendering, and built-in optimizations. The home page is an async Server Component that prefetches from Django and hydrates React Query · populated cards in the first byte. Locale-prefixed routes with localized slugs drive international SEO across 7 locales. TypeScript catches shape mismatches in API responses (financial data has many optional fields).
Trade-off: Heavier framework than a plain Vite SPA. Runs as a standalone Node.js server in production (port 3100) alongside Django. Worth it for SSR, SEO, and hreflang/i18n machinery.
TanStack Query (+ persistence)
Financial data is server state, not client state. Query handles caching, deduplication, background refetch, and stale-while-revalidate. The cache is also mirrored to localStorage (24h), so returning visitors paint instantly from disk while a soft revalidation runs.
Trade-off: Another abstraction layer. But eliminates entire categories of bugs (stale data, race conditions, cache invalidation) that would otherwise need manual management.
Server-side search (not Fuse.js)
The universe grew ~30× (from ~800 B3 stocks to 23K+ B3 + US listings) · an in-memory client-side index no longer made sense. Postgres trigram indexes answer fuzzy ILIKE queries in under a millisecond, results are cached 2 minutes in Redis, and the input debounces at 300ms.
Trade-off: A server round-trip per (debounced) keystroke instead of zero. Negligible against a warm cache, and the client no longer downloads the whole catalog upfront.
Recharts
React-native charting · components compose naturally. Good defaults for line charts (historical prices, year-end multiples). Responsive out of the box. Dynamically imported so its ~100KB loads only when the Charts tab opens.
Trade-off: Less customizable than D3. Can't do every exotic visualization. Sufficient for the chart types Sponda needs.
Tailwind CSS v4
Rapid styling with design constraints built in (spacing scale, color palette). Component-scoped CSS files with @apply keep JSX clean · no utility class soup in templates. Integrated via PostCSS.
Trade-off: @apply-only usage loses some of Tailwind's composability benefits. But gains readability · styles live in CSS files, not inline.
External Services
BRAPI + FMP + FRED
BRAPI is the only viable API for B3 (Brazilian exchange) data; FMP covers US tickers, statements, and daily FX rates; FRED supplies per-country CPI for inflation-adjusting foreign-currency financials. A routing layer (providers.py) picks the source per ticker so indicator code never knows which API fed it.
Trade-off: Three external dependencies for all financial data. Mitigated by layered caching (users see yesterday's data during an outage, not an error page) and per-provider circuit breakers with tight timeouts, so a hung API can't pin Gunicorn workers.
OpenAI (assistant)
Streaming Q&A on company pages plus a tool-calling screening agent, guardrailed to Sponda's finance domain by a cheap gpt-4o-mini pre-check before the gpt-4o answer.
Trade-off: Per-token cost with unpredictable usage. Contained by per-tier daily quotas, a question length cap, and a global daily USD spend cap that shuts the feature off rather than running up a bill.
Resend
Modern email API with good deliverability. SMTP integration means Django's built-in email backend works unchanged · verification, password reset, revisit reminders, and alert emails, localized per user. Simple pricing, no vendor lock-in on the code side.
Trade-off: Another SaaS dependency. But email delivery is not a problem worth solving in-house.
Sentry
One pane for errors, performance traces (frontend spans stitched to Django/Celery spans), Web Vitals, and cron monitoring · on the free tier. UptimeRobot covers the outside-in health check.
Trade-off: Sampling is tuned (hot routes at 1.0, everything else 0.2) to stay inside free-tier quota, so cold paths have thinner trace coverage.
Google OAuth (optional)
Reduces signup friction for users who don't want yet another password. Hidden by default · only appears when environment variables are configured.
Trade-off: Google dependency for auth. Mitigated by being optional · email/password always works. Users aren't locked in.
Infrastructure
systemd timers + Celery (split by shape)
Cron-shaped work (daily syncs, the 15-minute market-hours snapshot loop, weekly fundamentals) runs on systemd timers · visible in systemctl list-timers, logged in journald, persistent across reboots. Request-path background work (refreshing a stale ticker without making the user wait) runs on a Celery worker with retries and backoff, using the Redis that already serves the cache as its broker.
Trade-off: Two execution mechanisms instead of one. Each is the simplest tool for its half · moving the timers into Celery beat would add scheduling state for no gain, and doing stale-refresh in timers would leave users waiting on cold data.
Single server (not Kubernetes)
Four processes · Gunicorn, Next.js standalone, Celery worker, Redis · behind nginx on one DigitalOcean droplet. Deployment is git pull, install, restart via systemd · simple, fast, debuggable.
Trade-off: Single point of failure. No auto-scaling. Acceptable for the current user base. Vertical scaling (bigger server) is the first move if needed.
venv deploys (no Docker)
Every environment runs the code directly in a Python virtualenv · there is no Docker anywhere. Production: CI builds the Next.js bundle, the server does uv pip install into a venv and npm ci, and systemd restarts the services. Local dev: make dev runs Django (runserver 8710) and the Next.js dev server against a local venv and local Postgres. No image registry, no container runtime.
Trade-off: Host state (Python version, system packages) is not pinned by an image, and dev/prod parity rests on the deploy script rather than a shared image. Acceptable on a single long-lived droplet where the deploy script is the source of truth.
GitHub Actions
CI/CD lives next to the code. Free for public repos. Runs the three test suites in parallel jobs, builds the frontend bundle once in CI, deploys via SSH, and rebuilds the Hugo blog. No Jenkins server to maintain.
Trade-off: Vendor lock-in to GitHub. Workflows are YAML, not code. Acceptable · migration to another CI is straightforward if needed.
Testing
pytest + factory-boy
pytest's fixtures and parametrize are ideal for testing indicator calculations across many input scenarios. factory-boy generates realistic model instances · no fragile JSON fixtures to maintain.
Trade-off: factory-boy has a learning curve. Worth it · test data stays in sync with model changes automatically.
Playwright (not Selenium/Cypress)
Reliable auto-waiting, multi-browser support, and first-class Python integration via pytest-playwright. Tests auth flows, favorites, and page navigation end-to-end.
Trade-off: E2E tests are slow and occasionally flaky. Split from unit tests in CI to avoid session state leakage; pytest-rerunfailures and per-test timeouts keep flakes from blocking deploys.
Vitest (not Jest)
Fast, modern test runner with native TypeScript support. Compatible Jest API. Fast startup, watch mode works instantly.
Trade-off: Smaller ecosystem than Jest. Compatible API means migration is trivial if ever needed.
responses (HTTP mocking)
Mocks the requests library at the transport level. BRAPI/FMP/FRED tests run without network access · deterministic, fast, no API keys needed in CI.
Trade-off: Mocks can drift from the real API. Mitigated by lazy refresh in production · if a provider changes its response shape, the real app surfaces the error quickly.

Background work is hybrid: systemd timers for cron-shaped jobs (daily syncs, 15-min market-hours snapshots), Celery over Redis for request-path refresh (stale-while-revalidate · users get instant responses, workers re-pull providers behind the scenes). Nginx fronts everything: Next.js serves pages (port 3100), Django serves the API (Gunicorn, port 8710), Hugo serves the blog as flat HTML.
